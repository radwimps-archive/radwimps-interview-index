# RADWIMPS Archive　運用マニュアル

このマニュアルがあれば、サイトの公開から、記事の追加、リンク切れへの対応まで、AI に頼らず人の手で続けられるように書いています。

- パソコンは **Windows**、ブラウザは **Chrome か Edge** を使う前提です。
- スマホでもできる作業には「📱スマホでも可」と書いています。
- 費用はかかりません（GitHub の無料プランの範囲で動きます）。

## 1. しくみの全体像

- サイトのファイルは **GitHub**（ギットハブ）というサービスの「リポジトリ」（ファイルの置き場所）に置きます。
- 公開は **GitHub Pages** という無料の仕組みで行います。サーバーの管理はいりません。
- 記事の一覧は **`data/articles.csv`** という表のファイル1つです。ここを書き換えて保存すると、1〜2分でサイトに反映されます。サイトの **運営管理** から、記事を追加・修正してそのまま保存することもできます（9章）。
- トップの画面で、記事を探して読みます。
  - **探す入口**：「人から探す」「曲・作品から探す」「年代から探す」「ライブから探す」の4つ。押すとパネルが開き、下の記事一覧を絞り込みます。ライブは公演日ごとにまとめて表示します（公演日・ライブ名・会場の列を使います → 3-2）。探し方は一度に1つで、別の入口に切り替えると、前の入口で選んだもの（人・作品・年・ツアー）は外れます。同じ入口をもう一度押すとパネルが閉じますが、選んだものは残ります。検索の言葉と「さらに絞り込む」の条件は、入口を切り替えても残ります。
  - **検索** と **種類のタブ**：「記事・資料」「動画インタビュー」「リリース情報」「すべて」。どのタブに出るかは「種類」の列で決まります（3-2）。
  - **さらに絞り込む**：内容（カテゴリ）・人物・年代・掲載メディア・言語・資料の種類・読書の状態。パソコンでは左に、スマホでは一覧の上に折りたたんで出ます。
  - 記事は **カード** で12件ずつ並び、「続きを表示」で増えます。カードの右上のしおりで「あとで読む」、左下で「既読」。「説明を開く」を押すと、説明・メモ・タグが開きます。
- 左上の **メニュー**（3本線のボタン）には、記事一覧・あとで読む・記事を追加と、管理者の端末だけ **運営管理** が出ます（9章）。
- 絞り込みの状態は URL に入るので、そのままブックマークや共有ができます（例：`?person=野田洋次郎`）。運営管理は、URL の末尾に `#admin` を付けて開きます。以前の `#later`・`#videos`・`#c-tieup` などの URL も、そのまま使えます。
- タイトルを押すと、掲載元のページが新しいタブで開き、その記事は自動で「既読」になります。
- 保存するたびに、GitHub が自動で **書式チェック** をします。書き間違いがあると公開を止め、メールで知らせます（そのあいだも、サイトはひとつ前の状態で表示され続けます）。
- 毎週月曜の朝、GitHub が自動で **全記事のリンクを確認** し、開けなくなった記事があれば「Issue」（お知らせ欄）に一覧を書いて知らせます。

```
data/articles.csv を書き換えて保存
        │（自動）
        ▼
   書式チェック ── 問題あり ──▶ 公開を止めて、メールでお知らせ（サイトは前のまま）
        │ 問題なし
        ▼
   サイトに反映（1〜2分）


毎週月曜 9時ごろ（自動）
   リンクの確認 ── 対応が必要な記事あり ──▶ Issue でお知らせ
```

## 2. はじめての公開（最初の1回だけ）

用意するもの：Windows のパソコン、Chrome か Edge、メールアドレス、受け取った zip ファイル。

### 2-1. GitHub のアカウントを作る

1. <https://github.com/signup> を開き、メールアドレス・パスワード・ユーザー名を登録します。
2. **ユーザー名はサイトの URL の一部になります**（`https://ユーザー名.github.io/…`）。あとから変えると URL も変わるので、よく考えて決めてください。

### 2-2. リポジトリ（置き場所）を作る

> **何人かで運営する場合**は、先に「[12. 何人かで運営する（Organization）](#12-何人かで運営するorganization)」の 12-1 で Organization を作り、下の 1. で「**Owner**」をその Organization にしてください。サイトの URL は `https://Organization名.github.io/…` になります。

1. GitHub の画面右上の「**＋**」→「**New repository**」を押します。
2. **Repository name** に `radwimps-interview-index` と入れます（別の名前でもかまいません。URL の一部になります）。
3. 「**Public**」を選びます（一般公開のため）。
4. 「**Add a README file**」にチェックを入れます（空のままだと、次の設定がうまくできないことがあるため）。
5. 「**Create repository**」を押します。

### 2-3. 公開のしかたを設定する

1. 作ったリポジトリの上部の「**Settings**」を押します。
2. 左のメニューから「**Pages**」を押します。
3. 「**Build and deployment**」の「**Source**」で「**GitHub Actions**」を選びます（選ぶだけで設定されます）。

### 2-4. ファイルをアップロードする

1. 受け取った zip ファイルを右クリック →「**すべて展開**」します。
2. 展開してできた `radwimps-interview-index` フォルダを開き、**中身をすべて選びます**（Ctrl＋A）。
3. GitHub のリポジトリのトップページに戻り、「**Add file**」→「**Upload files**」を押します。
4. 選んだファイルとフォルダを、ブラウザの画面にドラッグ＆ドロップします。
5. 読み込みが終わったら、下の「**Commit changes**」を押します。

> ⚠ **`.github` フォルダも必ず入れてください。** 自動公開と自動チェックの設定が入っています。
> アップロード後、リポジトリのファイル一覧に `.github` があるか確かめてください。ない場合は [付録E](#e-自動公開の設定ファイルを手で作る) の方法で作れます。
>
> `README.md` は、2-2 で作ったものが上書きされます（それで正しいです）。

### 2-5. 公開されるのを待つ

1. リポジトリ上部の「**Actions**」を押します。
2. 「**サイトを公開する**」が動いています。黄色い丸（実行中）が **緑のチェック** になれば完了です（2〜3分）。
3. 赤い × になった場合は、[6章](#6-サイトを公開するが失敗したら) を見てください。2-3 の設定より先にアップロードした場合は、失敗した実行を開いて右上の「**Re-run all jobs**」を押せば、たいてい直ります。

### 2-6. サイトを開く

- 「**Settings**」→「**Pages**」の上部に「Your site is live at **https://…**」と URL が出ます。これがサイトの URL です。
- リポジトリのトップページにも URL を出しておくと便利です：右側の「About」の歯車 →「**Use your GitHub Pages website**」にチェック →「Save changes」。
- `README.md` の「公開サイト」の行も、この URL に書き換えておきましょう。

### 2-7. リンク切れチェックを一度動かしてみる

1. 「**Actions**」→ 左の一覧から「**リンク切れチェック**」を選びます。
2. 右側の「**Run workflow**」→ 緑の「**Run workflow**」を押します。
3. 数分で終わります。対応が必要な記事があれば、「**Issues**」に「リンク切れの可能性がある記事があります」というお知らせができます（[5章](#5-リンク切れのお知らせが来たら)）。

### 2-8. お知らせメールを確かめる

公開の失敗やリンク切れのお知らせは、GitHub に登録したメールアドレスに届きます。届かないときは、右上の自分のアイコン →「Settings」→「Notifications」で設定を確かめてください。

### 2-9. claude.ai 版の★と既読を引き継ぐ（使っていた場合）

1. 公開したサイトを開き、フッターの「**保存データの管理**」→「**ファイルから読み込む**」を押します（★は「あとで読む」として読み込まれます）。
2. zip と一緒に受け取った `bookmarks-backup.json` を選びます。
3. このファイルは **リポジトリにアップロードしないでください**（あなたの閲覧記録だからです）。

## 3. 記事を追加する

> **運営管理を使うと、サイトの中で記事を追加して、そのまま保存できます**（📱スマホでも可。最初に一度だけ「合鍵」の準備が必要です → [9章](#9-あとで読む既読と運営管理)）。
> この章は、GitHub の画面で `articles.csv` を書き換える方法です。書き方の決まり（3-2）と載せる記事の決まり（3-3）は、運営管理で追加するときも同じです。

### 3-1. いちばん簡単な方法：記事データ作成ツール（📱スマホでも可）

1. `https://ユーザー名.github.io/radwimps-interview-index/maker.html` を開きます（ブックマークしておくと便利です）。
2. URL・タイトル・媒体・掲載日などを入れると、下の「**できあがった1行**」に、そのまま貼り付けられる1行ができます。
   - 赤い「直してください」が出ていたら、その項目を直します。
3. 「**コピーする**」を押します。
4. GitHub でリポジトリを開き、`data` →`articles.csv` を開いて、右上の **鉛筆のアイコン**（Edit this file）を押します。
   - スマホのブラウザで見ているときは、鉛筆が「…」のメニューの中にあることがあります。
5. 1行目（見出しの行）の **行末** を押して改行し、**2行目に貼り付けます**。どこに入れても、サイトでは日付順に並びます。
6. 右上の「**Commit changes...**」→ もう一度「**Commit changes**」を押します。
7. 1〜2分後に、サイトを開き直して確かめます。

### 3-2. 直接書くときの決まり

`articles.csv` は、1行が記事1件です。項目は半角のカンマ（`,`）で区切ります。

```
状態,年,月,日,媒体,種類,カテゴリ,タイトル,URL,メンバー,対談相手,タグ,言語,メモ,説明,公演日,ライブ名,会場,id
公開,2026,11,4,〇〇マガジン,インタビュー,新作リリース、タイアップ,野田洋次郎が語る新作,https://example.com/article/123,野田洋次郎,,#夕星 #映画,日本語,,新作の制作の裏側を語るインタビュー。,,,,
```

| 列 | 書き方 | 例 |
|---|---|---|
| 状態 | `公開`・`非表示`・`リンク切れ` のどれか。空欄は「公開」 | 公開 |
| 年 | 西暦4桁。わからなければ空欄（「日付不明」として表示） | 2026 |
| 月 | 1〜12。わからなければ空欄 | 11 |
| 日 | 1〜31。わからなければ空欄（月がないときは書けません） | 4 |
| 媒体 | サイト名や雑誌名（**必須**） | 音楽ナタリー |
| 種類 | `インタビュー`・`対談・鼎談`・`特集・企画`・`雑誌・ムック`・`動画`・`番組・会見`・`ライブレポート`・`解説・メッセージ`・`ほかの人が語る`・`リリース情報` のどれか。空欄は「インタビュー」。**`動画` にすると「動画インタビュー」のタブに出ます**（YouTube の動画はこれにします）。**`リリース情報` は「リリース情報」のタブに出ます**（発売・公開のお知らせや、雑誌の掲載号の案内など、本文が読めない資料に使います）。`ライブレポート` は、ライブやイベントの様子を伝える記事に使い、メンバー列は `RADWIMPS`、対バンのゲストは対談相手の列に書きます（書き方は 3-3）。`ほかの人が語る` は、メンバー以外の人（共演者・スタッフ・ほかのアーティストなど）が RADWIMPS について語る記事に使い、メンバー列は空欄、話した人を対談相手の列に書きます | 対談・鼎談 |
| カテゴリ | 記事が生まれたきっかけ。`新作リリース`・`タイアップ`・`ライブ・ツアー`・`周年・節目`・`コラボ・楽曲提供`・`俳優・出演`・`楽器・ファッション`・`本・ドキュメンタリー`・`人物・素顔`・`ソロ・別プロジェクト` から、当てはまるものを **「、」で区切っていくつでも**。「さらに絞り込む」の「内容から選ぶ」は、この列で決まります。空欄だと、そこで絞り込んだときには出ません（書式チェックで「△ 注意」）。選び方は 3-3 | ライブ・ツアー、周年・節目 |
| タイトル | 記事のタイトル（**必須**） | |
| URL | `https://` から始まる記事の URL（**必須**） | |
| メンバー | `野田洋次郎`・`武田祐介`・`山口智史`・`桑原彰`・`RADWIMPS` を「、」で区切る。「野田」「武田」のような名字だけでも可。バンドとしての取材は `RADWIMPS` | 野田洋次郎、武田祐介 |
| 対談相手 | 対談の相手や、話している人の名前。「、」で区切る。ここに書いた名前は「人から探す」に並びます（森瑞希・エノマサフミ・白川詢は「サポートメンバー」として出ます） | 藤井道人、n-buna（ヨルシカ） |
| タグ | 作品名やテーマ。**1つずつ「#」を付けて**、半角スペースで区切る | #あにゅー #20周年 |
| 言語 | `日本語`・`英語`・`スペイン語`・`その他`。空欄は「日本語」 | 英語 |
| メモ | 「説明を開く」の中に小さく出る補足（日付の根拠、閲覧の条件、同じ公演のほかのレポートなど）。URL を書くとリンクになります。`参考資料：` で始めると、注意書きの枠で出ます。空欄でよい | 日付は公式サイトMEDIA欄の掲載日 |
| 説明 | 「説明を開く」で出る、記事の短い紹介文（1〜3文）。**掲載元の文章を書き写さず、自分の言葉で** 書きます（3-3）。空欄でよい | 映画の音楽づくりを語る対談。 |
| 公演日 | ライブレポートの公演日。`2025-12-27` のように年-月-日で（`2025/12/27` も可）。同じ公演日・ライブ名・会場の記事は「ライブから探す」でまとめて表示されます | 2025-12-27 |
| ライブ名 | ツアーやイベントの名前。同じツアーは同じ書き方にそろえます（「ライブから探す」の選択肢になります） | 20th ANNIVERSARY LIVE TOUR |
| 会場 | 公演の会場 | 有明アリーナ |
| id | **空欄でよい**（URL から自動で作られます）。あとで読む・既読の目印なので、一度決めたら変えないでください | |

**カンマと「"」のルール**

- 項目の中に **半角のカンマ「,」や「"」** があるときは、項目全体を `"` で囲み、中の `"` は `""` と2つ重ねます。
  - 例：`"Radwimps: ""We don't want to be a band you can define with one word"""`
- 全角の「、」「，」は、囲まなくてかまいません。
- 記事データ作成ツール（3-1）を使えば、この処理は自動でやってくれます。

### 3-3. 載せる記事・載せない記事

この索引には、**リンクを押すと、インタビューやライブレポートの中身（本文・発言・動画）が読める・見られるもの** を載せます。次のようなリンクは載せません。

| 載せないもの | 理由 |
|---|---|
| Apple Music・Spotify などの音楽サービスのページ | 押すとアプリが開き、記事が読めない |
| 雑誌の販売ページ（Fujisan・Amazon など）や、出版社の商品ページ | 買う前の紹介だけで、インタビューの中身が読めない（掲載号の案内として残したいときは、種類を `リリース情報` にして、タブを分けます） |
| 公式サイトの「掲載誌のお知らせ」だけのページ | どの雑誌に載ったかの一覧だけで、中身が読めない（残すときは、種類を `リリース情報` に） |
| ファンクラブ「ボクンチ」など、**有料会員限定**のコンテンツ | お金を払った会員しか読めない（無料の会員登録だけで読める記事は載せてよい） |
| 雑誌の発売を知らせるだけのニュース | 発言の引用がなく、中身が読めない（発言の一部が引用されている記事は載せてよい） |

- ボクンチ（bokunchi.radwimps.jp）の URL を「公開」の記事に書くと、書式チェックで「✗ エラー」になり、サイトの更新が止まります。
- Apple Music・Spotify・Amazon・Fujisan などの URL を「公開」の記事に書くと、書式チェックで「△ 注意」が出ます。
- YouTube の URL で、種類が「動画」になっていないときも「△ 注意」が出ます。
- 種類が `リリース情報` の行は、Amazon・Fujisan などの URL でも注意は出ません（本文が読めない資料として、タブを分けているため）。
- 載せないと決めた記事は、行を消すかわりに状態を `非表示` にし、メモ列に理由を書いておくと、同じ記事をうっかり追加し直すのを防げます。
  - 例：`非表示の理由：Apple Music のアプリが開き、記事が読めないため`

**ライブレポートの載せ方**

| こんなとき | どうするか |
|---|---|
| 載せるレポート | 公演の様子が何段落かで書かれているもの。セットリストだけの記事や、ライブ映像作品（DVD・Blu-ray）の発売を知らせるだけのニュースは載せません |
| 同じ公演のレポートが、いくつもの媒体にある | 1つを行にして、ほかの媒体名はメモ列に書きます（例：`同じ公演のレポートは BARKS にもあります`） |

| ステージにゲストで出たメンバーがいる | メンバー列に `RADWIMPS、山口智史` のように足すと、メンバーの絞り込みにも出ます |

**カテゴリの選び方**（記事が生まれたきっかけ。いくつ選んでもかまいません）

**説明（紹介文）の書き方**

- 本人の発言を入れたいときは、ごく短い言葉にとどめます。

### 3-4. Excel でまとめて編集する（パソコン）

たくさんの記事を一度に直すときに便利です。

1. GitHub で `data/articles.csv` を開き、右上の「**Download raw file**」（下向き矢印のアイコン）でダウンロードします。
2. Excel で開いて編集します。年・月・日は数字のまま入れます（Excel が勝手に日付の形に変えないよう、列を分けてあります）。
3. 「**名前を付けて保存**」→ ファイルの種類で「**CSV UTF-8 (コンマ区切り) (\*.csv)**」を選び、ファイル名は `articles.csv` のまま保存します。
   - ⚠ ただの「CSV (コンマ区切り)」を選ぶと文字化けします（その場合は書式チェックが止めて、知らせてくれます）。
4. GitHub の `data` フォルダを開き、「**Add file**」→「**Upload files**」で保存した `articles.csv` をドラッグし、「**Commit changes**」を押します。同じ名前なので上書きされます。

Google スプレッドシートを使う場合も同じ流れです：「ファイル」→「インポート」で読み込み、編集したら「ファイル」→「ダウンロード」→「カンマ区切り形式（.csv）」。ダウンロードしたファイルは名前を `articles.csv` に直してからアップロードします。

## 4. 記事を直す・非表示にする

- **運営管理から**：運営管理の「記事の管理」で記事を押し、直して「この内容にする」→「GitHub に保存」を押します（9章）。非表示・リンク切れ・削除もここでできます。（📱スマホでも可）
- **直す**：`articles.csv` を鉛筆アイコンで開き、その行を書き換えて「Commit changes」を押します。編集画面では左に行番号が出ます。（📱スマホでも可）
- **非表示にする**：その行の「状態」を `非表示` に書き換えます。サイトには出なくなりますが、行は残ります。
- **リンク切れにする**：記事が開けなくなったときは `リンク切れ` にします。リンク切れチェックが、開けるようになったときに知らせてくれます。
- **消す**：行ごと消してもかまいませんが、`非表示` にしておくほうが、同じ記事をうっかりもう一度追加するのを防げます。
- **記事を探す**：GitHub で `articles.csv` を開くと表の形で表示され、上の検索欄（Search this file…）で URL やタイトルの一部から探せます。編集画面では Ctrl＋F で探せます。

## 5. リンク切れのお知らせが来たら

毎週月曜の朝、対応が必要な記事があると、「**リンク切れの可能性がある記事があります**」という Issue ができます（メールでも届きます）。

### お知らせの見方

| 欄 | 意味 |
|---|---|
| 行 | `articles.csv` の何行目か（編集画面の行番号と同じ） |
| 掲載日・媒体・タイトル | どの記事か。タイトルを押すと記事が開きます |
| 判定の理由 | 「ページが見つかりません（404）」「別のサイトに転送されます」など |

### 対応のしかた

1. タイトルのリンクを開いて、本当に記事が見られないか確かめます。
2. **見られない** → その行の状態を `リンク切れ` に書き換えます。
3. **別の URL に移っていた** → URL を新しいものに書き換えます（状態は `公開` のまま）。
4. **問題なく見られた** → そのままで大丈夫です。毎回まちがって引っかかる記事は、メモ列に `リンク確認不要` と書くと、チェックの対象から外れます。
5. 「**開けるようになった記事**」の欄に出た記事は、`リンク切れ` にしていた記事が今は開けるものです。中身を確かめて `公開` に戻します。

すべて直すと、次のチェックで Issue は自動で閉じます（手で閉じてもかまいません）。

### 「要確認」の欄について

自動チェックを断るサイトや、応答が遅かったサイトが並びます。毎回同じサイトが出てくる場合は、そのサイトが自動チェックを受け付けていないと考えられます。たいていは問題ありません。この欄だけのときは Issue は作られず、「Actions」の実行結果のページで見られます。気になるものだけ、ときどき手で開いて確かめてください。

### 毎週のチェックが止まったら

リポジトリに **60日間** 変更がないと、GitHub が毎週の自動実行を止めることがあります（止まる前にメールが届くことがあります）。「**Actions**」→「**リンク切れチェック**」を開き、「**Enable workflow**」を押せば再開します。

### 手動でチェックする

「Actions」→「リンク切れチェック」→「Run workflow」→「Run workflow」。

## 6. 「サイトを公開する」が失敗したら

書き間違いがあると、公開が止まり「**Run failed: サイトを公開する**」というメールが届きます。「Actions」にも赤い × が付きます。**サイトは前の状態のまま表示され続けるので、あわてなくて大丈夫です。**

### エラーの読み方

1. 「**Actions**」で、赤い × の付いた実行を開きます。
2. 「**deploy**」→「**記事データの書式をチェックする**」を開くと、次のようなメッセージが出ています。

   ```
   ✗ エラー  data/articles.csv 12行目：日「30」は、2026年2月にない日付です
   ```

3. `articles.csv` のその行を直して「Commit changes」を押すと、自動でもう一度動きます。

実行結果のページの「Annotations」の欄にも、同じ内容が一覧で出ます。

### よくあるエラーと直し方

| メッセージ | 直し方 |
|---|---|
| 「"」で始めた項目が閉じられていません | `"` で囲んだ項目の閉じ忘れです。`"` の数を確かめます |
| 年「26」は4桁の西暦で書いてください | `2026` のように4桁で書きます |
| 日「30」は、2026年2月にない日付です | 日付を確かめます |
| 日を書くときは、月も書いてください | 月を入れるか、日を空欄にします |
| メンバー「〇〇」が分かりません | 書き間違いです。決まった名前（3-2の表）で書きます |
| URL は http:// か https:// で始め… | URL の先頭や、途中の空白を確かめます |
| id「〇〇」が △ 行目と同じです | 同じ記事を2回入れていないか確かめます。別の記事なら、片方の id を変えます |
| 状態「〇〇」は使えません | `公開`・`非表示`・`リンク切れ` のどれかにします |
| 文字コードが UTF-8 ではありません | Excel で「CSV UTF-8 (コンマ区切り)」を選んで保存し直します（3-4） |
| 1行目（見出し）に「媒体」の列がありません | 1行目の見出しを消したり変えたりしていないか確かめます |

「△ 注意」は、公開は止めませんが、確かめてほしい点です（例：タグに # が付いていない、同じ URL が2回ある）。

書式ではなく GitHub 側の一時的な問題で失敗することもあります。その場合は、失敗した実行を開いて右上の「**Re-run all jobs**」を押します。

### 7-2. 「RADWIMPSの歩み」（年表）を更新する

メニューの「**RADWIMPSの歩み**」（`history.html`）の年表は、`data/history.csv` に書いた出来事から作られます。新しいリリースやツアーが決まったら、1行足します（どの行に足しても、年表では日付順に並びます）。

```
年,月,日,終了年,終了月,終了日,カテゴリ,出来事,補足,特設サイト,タワーレコード,動画
2025,10,18,2025,12,27,ライブ・ツアー,「RADWIMPS 20th ANNIVERSARY LIVE TOUR」開催,9都市17公演,https://radwimps.jp/20th_TOUR/,,
2016,11,23,,,,リリース,8th Album「人間開花」リリース,,,RADWIMPS 人間開花,MV「光」=WuU6C8oXzIA | MV「前前前世 [original ver.]」=vLGQQbjZc5A
```

- **カテゴリ** は `リリース`・`ライブ・ツアー`・`映画・タイアップ`・`バンドの出来事`・`野田洋次郎・ソロ`・`山口智史・VXD` から書きます。上のタブは、このカテゴリで分かれます。
  - 2つ以上に当てはまるときは「、」で区切って書きます（例：`山口智史・VXD、ライブ・ツアー`）。書いたカテゴリのどのタブにも出ます。「すべて」のタブでは、はじめに書いたカテゴリの色の点がつきます。
  - `野田洋次郎・ソロ` は、illion と、野田洋次郎の名義での作品・ライブの行に使います（RADWIMPS の作品は `リリース` に）。ここに MV をつけると、MV のタブにも「野田洋次郎・ソロ」の印つきで並びます。
  - `山口智史・VXD` は、山口智史の活動休止と、VXD（声でバスドラムを鳴らす技術）を使った研究・演奏・ツアーの行に使います。
  - サポートメンバー（森瑞希・エノマサフミ・白川詢など）が加わった行は、`バンドの出来事` に書きます。
- ツアーなど期間があるものは、「終了年・終了月・終了日」に最終日を書きます（1日だけなら空欄）。
- 日がわからなければ「日」を空欄にします（「10月」と表示されます）。
- 「補足」は小さく出る一言です。なくてもかまいません。
- 「**タワーレコード**」には、タワーレコードで検索する言葉（例：`RADWIMPS 人間開花`）を書きます。
  - 「出来事」の中の**いちばん初めの「」か『』の中の作品名**が、点線の下線つきのリンクになります（上の例なら「人間開花」）。押すと、タワーレコードの検索結果（CD・初回盤・Blu-ray など）が新しいタブで開きます。
  - 商品ページの URL（`https://tower.jp/item/…`）を書けば、その商品のページが直接開きます。
  - 配信だけの曲は、タワーレコードでは売っていないので空欄にします（作品名はリンクになりません）。
  - タワーレコードで見つからない作品は、「タワーレコード」を空欄にして、「特設サイト」に公式の作品ページ（レーベルの商品ページなど）の URL を書きます。作品名が、そのページへのリンクになります（例：「RADWIMPS4.5」）。
  - スマホでスクロールしている途中や、止まった直後に作品名に触れても、リンクは開かないようにしてあります（誤って開くのを防ぐため）。
- 「**特設サイト**」には、ライブの特設サイトの URL を書きます（ライブ・ツアーの行）。「出来事」のいちばん初めの「」の中のライブ名が、点線の下線つきのリンクになります。
  - 特設サイトがないライブは、公式サイトのライブ情報のページ（`https://radwimps.jp/live/…/`）を書きます。
- 「**特設サイト**」は、映画・ドラマなどタイアップの行では、その作品の公式サイトの URL を書きます（作品名がリンクになります）。
- 「**動画**」には、YouTube の動画を「`ラベル=動画の ID か URL`」の形で書きます。いくつか書くときは「` | `」で区切ります。
  - 例：`MV=XRnX65LDRoU`（ラベルを省くと「MV」）、`MV「光」=WuU6C8oXzIA | MV「前前前世 [original ver.]」=vLGQQbjZc5A`、`予告編=https://www.youtube.com/watch?v=k4xGqY5IDBE`
  - 出来事の下に「▶ MV」などが小さく出て、押すとその場で再生されます（もう一度押すか「閉じる」で閉じます）。
  - 動画の ID は、YouTube の URL の `watch?v=` のうしろの11文字です。
  - 公開が終わった動画や、ほかのサイトでの再生（埋め込み）ができない動画は載せないでください。
  - ラベルが「MV」で始まる動画は、上の「**MV**」のタブに、1曲ずつ自動で並びます（曲名はラベルの「」の中、ラベルが「MV」だけのときは出来事の「」の中の名前）。
- リンクは `https://` で始まるものだけが使われます。
- 載せるのは、公式の発表などで日付を確かめられた出来事だけにします。

#### タワーレコードのアフィリエイトを始めるとき

1. バリューコマース（<https://www.valuecommerce.ne.jp/>）に登録し、管理画面から「TOWER RECORDS ONLINE」に提携を申し込みます（審査があります）。
2. 承認されたら、`assets/config.js` の `towerAffiliate` に、バリューコマースの管理画面に出る **sid** と **pid** の数字を書いて保存します。
   ```
   towerAffiliate: { sid: "1234567", pid: "890123456" }
   ```
3. 1〜2分たつと、年表の作品名のリンクがすべてアフィリエイトリンクになり、作品名の横とページの上下に「**PR**」の表示が出ます（広告であることをはっきり示すのは、タワーレコードの提携条件と、いわゆるステマ規制で決められています）。
- やめるときは、sid と pid を `""`（空欄）に戻します。
- リンクの形がバリューコマースの管理画面の案内と違うときは、`assets/history.js` の `towerUrl` を直します（わからなければ、管理画面で作ったリンクの例を1つ控えておき、詳しい人や AI に見せてください）。

## 9. あとで読む・既読と運営管理

- あとで読む（カードの右上のしおり）・既読（左下の ○／✓）は、**見ている人のブラウザの中だけ** に保存されます。サーバーには送られず、ほかの人からは見えません。数はフッターの「保存データの管理」で見られます。
- タイトルや媒体名を押して記事を開くと、自動で既読になります。既読のカードは淡い緑になります。
- 別の端末に移すときや、ブラウザのデータを消す前は、「保存データの管理」でファイルに書き出し、移った先で読み込みます。
- 以前のデザインの「お気に入り（☆）」は、「あとで読む」にまとめました（以前のバックアップファイルを読み込んだときも同じです）。
- ブラウザの「閲覧履歴データの削除」で Cookie とサイトデータを消すと、これらの記録も消えます。
- 記事の `id` を変えると、その記事の記録は外れます。

### 管理者モード（運営管理を自分の端末にだけ出す）

GitHub Pages のサイトにはログインの仕組みがないため、運営管理は「管理者モードをオンにした端末」にだけ出します。

1. 自分のスマホやパソコンで、サイトの URL の末尾に `#admin` を付けて開きます（例：`https://ユーザー名.github.io/radwimps-interview-index/#admin`）。
2. 「**この端末で管理者モードをオンにする**」を押します。メニューに「**運営管理**」が出ます。
3. 運営管理には、記事データの状態（公開・非表示・リンク切れの数、書式チェックの結果）、**記事の管理**（次の節）、よく使う GitHub の画面へのリンクがあります。
4. オフにするときは、運営管理か「保存データの管理」の「管理者モードをオフにする」を押します。

- 管理者モードは「この端末に運営管理を出す」だけの設定です。記事を書き換えるには、次の節の「**合鍵**」が必要です。ほかの人が管理者モードをオンにしても、合鍵がなければ何も変えられません。
- 訪問者の「記事を追加」は、追加のお願いを GitHub の Issue で送る画面です（送る人は GitHub のアカウントが必要です）。届いたお願いは、運営管理の「届いた依頼・お知らせを見る」から確かめます。

### 運営管理で記事を追加・修正する

運営管理の「**記事の管理**」では、記事の追加・修正・非表示・削除をして、そのまま GitHub に保存できます（📱スマホでも可）。保存すると、GitHub の画面で `articles.csv` を書き換えたときと同じように、書式チェックのあと1〜2分でサイトに反映されます。

#### 最初に一度だけ：合鍵を作って登録する

「合鍵」は、運営管理がこのサイトの記事データを書き換えるための、GitHub の **アクセストークン**（Fine-grained personal access token）です。

1. 運営管理の「記事の管理」にある「**GitHub の合鍵を作る画面**」を押します（GitHub にログインした状態で開きます）。名前・説明・有効期限（90日）・許可（Contents の読み書き）が入った状態で開きます。
2. 「**Repository access**」で「**Only select repositories**」を選び、「Select repositories」からこのサイトのリポジトリ（`radwimps-interview-index`）だけを選びます。
3. 「**Permissions**」に「**Contents**」の「**Read and write**」があることを確かめます。
4. いちばん下の「**Generate token**」を押します（確認が出たら、もう一度押します）。
5. `github_pat_` から始まる合鍵が表示されるので、コピーします。**この画面を離れると、二度と表示されません。**
6. 運営管理に戻り、「リポジトリ」の欄が `ユーザー名/radwimps-interview-index` になっていることを確かめて（ふつうは最初から入っています）、「合鍵（アクセストークン）」の欄に貼り付け、「**GitHub とつなぐ**」を押します。
7. 「GitHub につながっています」と出て、記事の一覧が出れば完了です。この端末では、次からは自動でつながります。

> 合鍵を作る画面を自分で開くとき：GitHub の右上の自分のアイコン →「Settings」→ 左のメニューのいちばん下「Developer settings」→「Personal access tokens」→「Fine-grained tokens」→「Generate new token」。この場合は、名前（Token name）・有効期限（Expiration）を入れ、Permissions の「Contents」を「Read and write」にします。

#### 記事を直す・非表示にする・消す

1. 一覧の記事を押すと、編集画面が下から出てきます。上の検索欄（タイトル・媒体・URL で探す）や、「公開」「非表示」「リンク切れ」「要確認」のボタンで探せます。
2. 書き換えたら「**この内容にする**」を押します。赤い「直してください」が出ているあいだは押せません（書き方の決まりは 3-2・3-3 と同じです）。
3. 非表示・リンク切れにするときは、編集画面のいちばん上の「状態」を選びます。
4. 消すときは「**削除**」→「**削除する**」。かわりに「**非表示にする**」を選ぶと、同じ記事をうっかり追加し直すのを防げます。

#### 記事を追加する

1. 「**＋ 記事を追加**」を押します（メニューの「記事を追加」からも開けます）。
2. URL・タイトル・媒体・掲載日・種類・カテゴリ・メンバーなどを入れて、「**追加する**」を押します。
   - YouTube の URL を入れると、種類と媒体が「動画」「YouTube」になります。
   - id は空欄のままで大丈夫です（URL から自動で作られます。[付録G](#g-記事データの-id-についてくわしく)）。

#### 保存する

1. 直したり追加したりした内容は、まだ GitHub には送られていません。画面の下に「**保存していない変更 ◯ 件**」と出ます。
2. 「**GitHub に保存**」を押します。1〜2分でサイトに反映されます。
   - 変更をやめるときは、「**取り消す**」を押して、続けてもう一度押します。
   - GitHub の履歴（`articles.csv` の「History」）には「記事データを更新（運営管理から：追加 1・修正 0・削除 0）」のような名前で残ります。
   - 保存すると、`articles.csv` の行は掲載日の新しい順に並べ直されます。
- 保存していない変更は、ページを閉じたり読み込み直したりすると消えます。こまめに保存してください。
- 運営管理を開いているあいだに、パソコンなど別の場所で `articles.csv` が書き換えられていても、保存のときに自動で最新の内容に重ねます。同じ記事をどちらでも直していたときは、運営管理で直した内容が残ります。

#### 合鍵の期限が切れたら・使えなくなったら

- 「**合鍵（アクセストークン）が正しくないか、期限が切れています**」と出たら、上の手順 1〜6 で新しい合鍵を作って、登録し直します。保存していない変更は残っていて、つなぎ直すと続きから保存できます。
- 「**この合鍵には、記事データを書き換える許可がありません**」と出たら、「Contents」が「Read and write」になっていない合鍵です。作り直して、登録し直します。
- 期限が近づくと、GitHub からお知らせのメールが届きます。
- 使わなくなった合鍵は、GitHub の「Fine-grained tokens」の画面で「**Delete**」を押して消せます。

#### 安全のために

- 合鍵は、登録した端末のブラウザの中にだけ保存されます。サイトを見に来た人には見えず、GitHub 以外には送られません。
- 合鍵があれば、このサイトの記事データを書き換えられます。人に教えたり、共用のパソコンで登録したりしないでください。作るときに選ぶリポジトリも、このサイトのものだけにします（Only select repositories）。
- その端末で使わなくなったら、運営管理の「**合鍵を消す**」を押します。端末をなくしたときは、GitHub の「Fine-grained tokens」の画面でその合鍵を「Delete」すると、すぐに使えなくなります。

#### 合鍵なしで試す

- 「**保存せずに試す**」を押すと、合鍵なしで一覧と編集画面を試せます。変更は GitHub に保存されません。
- 試した変更は「**ファイルに書き出す**」で `articles.csv` として保存できます。GitHub の `data` フォルダに上書きでアップロードすれば反映されます（パソコン向け）。
- claude.ai のプレビュー版では GitHub につなげないため、「保存せずに試す」だけが使えます。

| 困りごと | 確かめること |
|---|---|
| 直したのにサイトが変わらない | 「Actions」の「サイトを公開する」が緑になるまで待ち、ページを読み込み直します（パソコンは Ctrl＋F5、スマホはタブを閉じて開き直す） |

## 11. 付録

### A. 用語集

| 用語 | 意味 |
|---|---|
| リポジトリ | GitHub 上のファイルの置き場所。変更の履歴もすべて残ります |
| コミット（Commit changes） | 変更を保存すること。保存のたびに履歴が1つ増えます |
| GitHub Actions・ワークフロー | GitHub が自動で動かしてくれる処理。このサイトでは「サイトを公開する」と「リンク切れチェック」の2つ |
| Issue（イシュー） | リポジトリのお知らせ・連絡の欄。リンク切れのお知らせや、見た人からの連絡が届きます |
| GitHub Pages | GitHub の無料のサイト公開の仕組み |
| CSV | カンマで区切った表のファイル。Excel やメモ帳で開けます |
| UTF-8 | 文字コード（文字の記録のしかた）の一種。このサイトの CSV はこれで保存します |
| 合鍵（アクセストークン） | 運営管理が GitHub の記事データを書き換えるための、`github_pat_` から始まる文字。GitHub で作り、使う端末にだけ登録します（9章） |

### B. 見た人からの連絡

サイトのフッターの「こちらから知らせてください」から、見た人が Issue で誤りやリンク切れを知らせられます（相手に GitHub のアカウントが必要です）。届いた Issue は「Issues」タブで読み、対応したら「Close issue」で閉じます。

### C. チェック用プログラムを自分のパソコンで動かす（任意）

ふだんは GitHub が自動で動かすので不要です。

1. Node.js をインストールします（<https://nodejs.org/ja> の「LTS」と書かれたもの）。
2. GitHub のリポジトリのトップで「**Code**」→「**Download ZIP**」でファイル一式をダウンロードして展開します。
3. 展開したフォルダを開き、アドレスバーに `powershell` と入力して Enter を押します。
4. 次のどちらかを入力して Enter を押します。
   - 書式チェック：`node tools/validate.mjs`
   - リンク確認：`node tools/check-links.mjs`

### D. パソコンでサイトを表示して確かめる（任意）

1. Visual Studio Code（<https://code.visualstudio.com/>）をインストールします。
2. 左の拡張機能のアイコンから「**Live Server**」を検索してインストールします。
3. 「ファイル」→「フォルダーを開く」で、サイトのフォルダを開きます。
4. `index.html` を右クリック →「**Open with Live Server**」。ブラウザでサイトが開きます。

### E. 自動公開の設定ファイルを手で作る

アップロードで `.github` フォルダが入らなかったときの方法です。

1. リポジトリのトップで「**Add file**」→「**Create new file**」を押します。
2. ファイル名の欄に `.github/workflows/deploy.yml` と入力します（`/` を打つと、自動でフォルダの区切りになります）。
3. zip の中の同じ名前のファイル（`.github` → `workflows` → `deploy.yml`）をメモ帳で開き、全部コピーして、GitHub の編集欄に貼り付けます。
4. 「**Commit changes**」を押します。
5. `.github/workflows/check-links.yml` も、同じ手順で作ります。

### F. ほかの人に運営を手伝ってもらう

何人かで運営するときは、「[12. 何人かで運営する（Organization）](#12-何人かで運営するorganization)」のやり方がおすすめです（全員が運営管理を使えます）。

個人のリポジトリのまま手伝ってもらうこともできますが、その人は運営管理からは保存できず、GitHub の画面で `articles.csv` を書き換えることになります。

1. 「**Settings**」→「**Collaborators**」→「**Add people**」で、相手の GitHub のユーザー名かメールアドレスを入れて招待します。
2. 招待を受けた人は、自分のアカウントで記事の追加や修正ができるようになります。
3. お知らせを受け取ってもらうには、リポジトリの上部の「**Watch**」を設定してもらいます。

### G. 記事データの id について（くわしく）

- id は、あとで読む・既読がどの記事のものかを見分ける目印です。
- 空欄にすると、URL から `u-` で始まる id が自動で作られます。この場合、あとで URL を直すと id も変わり、その記事の記録は外れます。
- 最初から入っている記事には、`ro-216064` のような id が付いています。消したり変えたりしないでください。

## 12. 何人かで運営する（Organization）

**Organization**（オーガニゼーション）は、GitHub のチーム用の置き場所です（無料）。リポジトリを Organization に置くと、招いたメンバー全員が、自分の合鍵で運営管理から記事を保存できます。

### 12-1. Organization を作る（あなたが1回だけ）

1. GitHub の右上の自分のアイコン →「**Your organizations**」→「**New organization**」を押します。
2. 「**Free**」（無料）を選びます。
3. **Organization name** を決めます（例：`radwimps-archive`）。**サイトの URL の一部になります**（`https://radwimps-archive.github.io/…`）。
4. 連絡先のメールアドレスを入れ、「**My personal account**」（自分の個人アカウントのもの）を選んで作ります。メンバーを招く画面が出たら、あとで招くので「Skip」で大丈夫です。

### 12-2. リポジトリを Organization に置く

- **まだ公開していない場合**：2章の 2-2 で、「Owner」をその Organization にしてリポジトリを作ります。そのあとは2章のとおりです。
- **もう個人のアカウントで公開している場合**：リポジトリの「**Settings**」→ いちばん下の「**Transfer**」→ Organization を選んで移します。
  - サイトの URL が `https://Organization名.github.io/…` に変わります。古い URL からは自動で移動しないので、知らせている人には新しい URL を伝えます。
  - 移したあと「Settings」→「Pages」の「Source」が「**GitHub Actions**」になっているか確かめます（2-3）。なっていなければ選び直します。
  - `README.md` の公開サイトの URL と、使っている人がいれば運営管理の合鍵も作り直します（持ち主が変わるため）。

### 12-3. メンバーを招く

1. 手伝う人に GitHub のアカウントを作ってもらい、ユーザー名を教えてもらいます。
2. Organization のページ →「**People**」→「**Invite member**」で、その人のユーザー名を入れて招きます。役割は「**Member**」にします（「Owner」は Organization の設定も変えられるので、あなただけにしておきます）。
3. リポジトリの「**Settings**」→「**Collaborators and teams**」→「**Add people**」で、その人に「**Write**」の権限を付けます。
4. 招待メールで「Join」を押してもらいます。

### 12-4. メンバーが運営管理を使えるようにする（メンバーそれぞれ）

1. 自分の端末で、サイトの URL の最後に `#admin` を付けて開き、管理者モードをオンにします（9章）。
2. 「GitHub の合鍵を作る画面」を開きます。「**Resource owner**」（持ち主）が Organization になっていることを確かめます（運営管理から開くと、最初から入っています）。
3. あとは9章の手順で合鍵を作って登録します。
4. 合鍵が「**承認待ち**（pending）」になったときは、Organization の Owner（あなた）が Organization の「**Settings**」→「**Personal access tokens**」→「**Pending requests**」で承認します。承認されるまでは保存できません。

### 12-5. 共同運営のきまり

- 合鍵は一人ひとりが自分で作ります。**合鍵を人に渡したり、借りたりしない**でください。
- 運営をやめる人が出たら、Organization の「**People**」でその人を外します。その人の合鍵も使えなくなります。
- だれがいつ何を変えたかは、`articles.csv` の「**History**」でわかります。間違いがあっても、10章の方法で前の状態に戻せます。
- 載せる記事の決まり（3-3）は、メンバー全員で同じものを使います。新しいメンバーには、まず3章と9章を読んでもらってください。
